## 如何读这些数值

- **每路 TG**：引擎报告的 `(输出 token - 1) / 该请求 prefill 结束至生成结束的秒数`。先取每批各路中位数，再取两轮中位数；时间包含并发时与其他流共享执行资源的等待。
- **总生成吞吐**：`Σ(各路输出 token - 1) / (最后一路请求结束 - 最早可见 token)`。这是批次生成时间窗吞吐，不是把各路 TG 相加；部分其他流的 PP 可能落在此时间窗内。
- **PP**：`Σ(输入 token - 命中 token) / (最后一路首 token - 最早请求提交)`。这是客户端观测的整批有效 PP，包含 tokenization、排队、恢复和并发调度等待，不是 GPU kernel 的裸速度。热缓存按实际重算尾部计算，绝不把已命中输入再计入 PP 分子。
- 逐请求 CSV 另外保留 `prefill_s` 和 `stream_pp_tps`，后者是该请求重算 token / 引擎报告的 prefill_seconds。多个请求的这段时间可能重叠，不能相加当作整机 PP，也不能把它当作无等待的 GPU kernel 计时。
- **TTFT**：客户端收到第一段非空 content 或 reasoning_content 的时间。不是“第一段最终回答”的时间。表中为每批各路中位数的两轮中位数。
- **全部完成**：最早提交至最后一路请求结束。**端到端总输出吞吐**为所有输出 token / 全部完成时间，包含冷 PP 和所有等待。
- 两轮不足以估计 p95/p99 或稳定负载服务能力。下面同时提供观测范围和完整逐路数据；1–4 路是同步突发请求数，不是到达率压测。

## 缓存、并发与有效性校验

每个单元先清空前缀缓存，再同步提交 N 个独立请求，全部结束后原样重复一次作为热缓存。这里的“冷”仅指前缀缓存没有可复用状态；模型已经加载和预热，不清空系统页缓存或 Engram 的操作系统缓存，也不计模型启动时间。使用线程 barrier，实际提交时间差保留在数据中。清理、tokenize 和预热请求不计入速度表。清缓存通过短请求申请完整 KV 逻辑容量完成，仅用于独占测试端口，不能对正在服务用户的端口运行此脚本。测试过程中采集引擎计数及双机 GPU 状态；worker 上原有 embedding 服务保持常驻，其测试窗口日志未出现 POST 推理请求。

- 全部 160 条计时请求均输出 1024 token；冷请求命中 0，热请求均命中其最长可复用检查点。
- 冷／热相同请求的输出 token 哈希全部一致；全部单元的请求完成计数与脚本请求数相符，未混入其他生成请求；restore 失败增量为 0。
- 批次内最大提交时间差为 7.834 ms。多路请求的流式输出均有重叠，具体时间和 running 峰值见逐批数据；这不等于多个 PP kernel 在 GPU 上同时执行。

构建参数见 [DEPLOYMENT.md](DEPLOYMENT.md)，运行参数见本页配置表。按该说明设置两节点的目录和互联信息，使用 `PORT=18892 TP_PORT=29622 CTX=1048576 PCACHE=2 PARALLEL=4` 隔离启动双节点引擎，两端 TP_PORT 必须一致。本次在 loopback 专用端口未设置 API_KEY_FILE。在 head 上运行公开的 [benchmark.py](../../tools/dsv41-rr/benchmark-20261026/benchmark.py)；需要 Python 3 标准库与无其他用户的专用测试服务。脚本会主动清空该服务的前缀缓存：

```bash
python3 benchmark.py --url http://127.0.0.1:18892 --model DeepSeek-V4.1-Flash-TF   --context 1048576 --rounds 2 --out results-thinking-on
# supplement.py 与 benchmark.py 放在同一目录；同一专用 18892 服务。
python3 supplement.py results-thinking-off --url http://127.0.0.1:18892 --model DeepSeek-V4.1-Flash-TF
```
